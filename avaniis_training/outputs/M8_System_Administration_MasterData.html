S1

Overview & Preconditions

System administration of AVANIIS HR — the master data hierarchy that all other modules depend on. These preconditions must be satisfied before any module can function correctly.

Module Purpose: Master Data Management (MDM) is the foundation layer. Every employee record, leave balance, payroll run, workflow approval, and org chart node traces back to entities configured here. A misconfigured master data hierarchy silently breaks downstream modules — this module teaches you to get it right the first time.
  • 1
    Super Admin user exists and is logged in — only SUPER_ADMIN can modify legal entities, custom fields, and SSO settings. /users → assign SUPER_ADMIN role
  • 2
    Microsoft Entra ID SSO configured — AZURE_AD_TENANT_ID, AZURE_AD_CLIENT_ID, and AZURE_AD_CLIENT_SECRET must be set. Entra ID is the only supported login method. /settings/sso → verify OIDC redirect URI
  • 3
    Default tenant_id set — all tables use a tenant UUID of 00000000-0000-0000-0000-000000000001. The environment variable MAG_TENANT_UUID must match. /settings/system → tenant configuration
  • 4
    At minimum 1 legal entity configured — the legal_entities table must have at least one active record before any employee can be created or any position can be attached to an entity. /master-data/legal-entities → verify active entities
  • 5
    Database migrations current — migration 0026 must be applied. Running an older migration set will cause missing columns for is_frozen, is_confidential, vacancy_start_date, and acting fields. /settings/system → migration status panel
  • 6
    Cron jobs running — the Vercel cron at 09:00 UTC handles workflow SLA timers, probation checks, and org snapshots. If CRON_SECRET is missing, all cron endpoints return 401. /api/cron/* — check vercel.json cron schedule
  • 7
    SMTP configured for notifications — SMTP_HOST, SMTP_PORT, SMTP_USER, and SMTP_PASS must all be set. Missing SMTP causes silent notification failures; approval emails never reach approvers. /settings/notifications → SMTP test button

Blocking Conditions — system will not function correctly until resolved

  • No legal entity → cannot create any employee
  • No grade salary band → promotions are blocked
  • SSO misconfigured → no user can log in
  • is_frozen=true on position → all assignments to that position blocked
  • Missing migration 0026 → vacancy_start_date column absent → org chart errors
  • CRON_SECRET absent → workflow SLA timers never fire → approvals stall

Dependency Map

Three configuration chains govern how master data flows through every module. Understanding these chains prevents silent failures and misconfigured setups.

CHAIN A — Core Employee Hierarchy
Legal Entity
→
Department
→
Grade + Salary Band
→
Job
→
Position
→
Worker Assignment
→
All Modules Work

Every single downstream module — Leave, Payroll, Timesheets, Org Chart, Approvals, ARIA — requires a complete CHAIN A. A break at any node in this chain propagates silently to all modules that depend on it. The legal entity is the root anchor; removing or deactivating a legal entity without migrating its positions and persons first will orphan records across 11 modules.

CHAIN B — Grade Salary Band Propagation
Grade salary band update
→
Existing positions recheck
→
Grade Band Validator updates
→
Finance sign-off required if above max
→
Payroll module uses new band

When a grade's salary band (min/mid/max) is updated, the system automatically rechecks all positions linked to that grade. Any employee whose current salary falls outside the new band is flagged. Finance must sign off before those employees can receive a promotion or salary increase. The Grade Band Validator enforces the rule: min < mid < max with no overlap between adjacent grades.

CHAIN C — Workflow Template Configuration
Workflow template config
→
Approval steps resolve
→
SLA timers apply
→
Delegation rules apply
→
All request types work

All approval-based request types — leave requests, hiring requests, transfer requests, salary change requests — rely on CHAIN C. A workflow template must be configured for each request type and for each legal entity. SLA timers are enforced by the cron job at /api/cron/workflow-sla. Delegation rules are applied when an approver is on leave. If no workflow template is configured for a request type, new requests enter PENDING_APPROVAL state permanently and can never advance.

Visual: Module Dependency Flow

Important: Chains A, B, and C are not independent. A broken CHAIN A prevents CHAIN B validation from running because there are no positions to validate. Always establish CHAIN A completely before configuring workflow templates (CHAIN C).
S3

Entity Type Cards

Six master data entities form the backbone of the AVANIIS HR system. Each entity has specific access controls, bilingual requirements, and cascading impact on downstream modules.

🏢
Legal Entities
/master-data/legal-entities
Edit permission: SUPER_ADMIN only
Bilingual: name_en + name_ar required on every record. The Arabic name appears on payslips and official letters.
Key fields: trade_licence_number, legal_type (LLC / FZ / Branch / Holding), incorporation_date, is_active
Relation: All departments, positions, and persons must be linked to a legal entity via legal_entity_id. The default tenant UUID is embedded at row level.
Breaks if missing: No employee can be created. All HR processes halt at entity validation.
SUPER_ADMIN write · HR_ADMIN read-only
🏗️
Departments
/master-data/departments
Edit permission: HR_ADMIN and above
Bilingual: name_en + name_ar mandatory. The self-referencing parent_department_id column enables unlimited nested hierarchy (e.g. Avaniis → Technology → Software Engineering).
Key fields: department_code, cost_centre, parent_department_id (self-ref FK), head_position_id, is_active
Relation: Positions reference departments. The org chart uses the department hierarchy to build the tree. Department reparenting (changing parent_department_id) moves all child departments and their positions.
Breaks if missing: Positions have no department home. Org chart cannot render subtrees.
HR_ADMIN write · Manager read-only
📊
Grades & Salary Bands
/master-data/grades
Edit permission: HR_ADMIN + Finance sign-off for band changes
Bilingual: name_en + name_ar. Grade codes follow the convention G1–G12 by default but are configurable per entity.
Key fields: grade_code, rank_order, min_salary, mid_salary, max_salary (all stored in AED). The grade_salary_ranges table stores effective-dated band history.
Grade Band Validator: Automatically runs on every save. Enforces min < mid < max. Flags any employee whose current salary is outside the band. Finance is notified via the Postgres outbox.
Breaks if missing: All promotion and salary change workflows are blocked. Payroll cannot validate compensation.
HR_ADMIN write · Finance notification · SUPER_ADMIN override
💼
Jobs
/master-data/jobs
Edit permission: HR_ADMIN and above
Bilingual: job_title_en + job_title_ar. The Arabic job title is used on official employment contracts and salary certificates.
Key fields: job_code (unique per entity), job_family (Engineering / Finance / HR / Operations / Legal / Executive), job_level, is_managerial, typical_grade_id
Relation: Positions reference a job_id. The job defines the nature of the work; the position is a specific seat in the org chart. One job may be used by many positions (e.g. "Software Engineer" appears 12 times in Technology).
Breaks if missing: No positions can be created. Hiring requests cannot specify a job title.
HR_ADMIN write · All roles read
📍
Positions
/master-data/positions
Edit permission: HR_ADMIN and above
Special flags: is_frozen (boolean — budget hold, no assignments allowed), is_confidential (boolean — hidden from public org chart), vacancy_start_date (auto-set when OCCUPIED → VACANT transition occurs)
Key fields: position_code, reports_to_position_id (self-ref), department_id, job_id, grade_id, headcount_budget, is_frozen, is_confidential, vacancy_start_date
Lifecycle: DRAFT → ACTIVE → OCCUPIED → VACANT → FROZEN → ARCHIVED. See Section 5 for the full state machine with transition rules.
Breaks if missing or frozen: All assignments to this position are blocked. Hiring requests cannot be raised against a frozen position.
HR_ADMIN write · Confidential positions hidden from Managers + Employees
⚙️
Custom Fields
/settings/custom-fields
Edit permission: SUPER_ADMIN only
Applies to: persons table or worker_assignments table. Custom fields allow client-specific data capture without schema changes.
Field types supported: TEXT, NUMBER, DATE, BOOLEAN, SELECT (single), MULTI_SELECT, URL. All custom field values are stored as JSONB in the custom_fields column of the target table.
Bilingual labels: label_en + label_ar. Labels appear in employee profiles, import templates, and HR reports.
Breaks if removed mid-use: Existing data is orphaned in JSONB. Reports that reference the field by key will return null values.
SUPER_ADMIN only — HR_ADMIN cannot modify field schema
Setup order matters: Always create entities in CHAIN A order — Legal Entity first, then Departments, then Grades, then Jobs, then Positions. Creating a Position before its Department exists will produce a foreign key violation that rolls back the entire transaction.

Position Lifecycle State Machine

Every position in AVANIIS HR moves through a defined set of states. Understanding these transitions is critical for org chart integrity, hiring, and budget management.

DRAFT
→
ACTIVE
→
OCCUPIED
→
VACANT
→
FROZEN
→
ARCHIVED
DRAFT
Position just created. Not yet visible in the public org chart. No assignments allowed. HR_ADMIN is configuring the position details (reports_to, grade, job code). The position exists in the database but vacancy_start_date is null.
ACTIVE
Position is open and available for assignment. vacancy_start_date is auto-set to the activation date. The position appears in the org chart as a vacant node (red indicator in the org chart canvas). Hiring requests can be raised against ACTIVE positions.
OCCUPIED
A worker_assignment record links a person to this position. The position appears in the org chart with the employee's name and photo. is_acting=true on the assignment indicates an acting (temporary) occupant. vacancy_start_date is null while occupied.
VACANT
The previous occupant has departed or been transferred. vacancy_start_date is auto-set by the system when the assignment is end-dated. The position shows in the org chart as vacant. ARIA can report "positions vacant for >90 days" using vacancy_start_date.
FROZEN
is_frozen=true is set by an HR Director or SUPER_ADMIN — typically during budget freezes or restructuring. No new assignments are allowed. No hiring requests can be raised. The position shows an amber warning banner in the org chart. A freeze_reason text field captures the business rationale.
ARCHIVED
Position is decommissioned. Cannot be reactivated. Historical assignments remain in the database for audit purposes (records are never deleted — effective-date pattern). is_confidential=true positions may be archived when confidential roles are dissolved.

State Transitions & Rules

→
DRAFT → ACTIVE
HR_ADMIN explicitly activates the position. System sets vacancy_start_date = today. Position becomes visible in org chart as a vacant node.
→
ACTIVE → OCCUPIED
A worker_assignment record is created linking person_id and position_id. vacancy_start_date is set to null. The org chart node transitions from red (vacant) to the employee card.
→
OCCUPIED → VACANT
Assignment is end-dated (departure, transfer, or role elimination). System auto-sets vacancy_start_date. Position returns to the org chart as a vacant node. The previous assignment record is preserved with effective_to date set.
→
VACANT → FROZEN
HR Director sets is_frozen=true with a freeze_reason. No hiring requests can now be raised. The position displays an amber FROZEN badge in the org chart. Finance is notified via outbox.
→
FROZEN → ACTIVE
HR Director sets is_frozen=false (unfreeze). Requires a workflow approval step with Finance sign-off. The position returns to ACTIVE (VACANT) status and can accept hiring requests again.
→
ACTIVE → ARCHIVED
Position is decommissioned by SUPER_ADMIN. Only possible when position is ACTIVE (no current occupant). All historical assignment records are retained with is_archived=true on the position record.
→
VACANT → ACTIVE (re-list)
A vacant position can be explicitly re-listed for hiring even if it was previously OCCUPIED and then became VACANT. This is equivalent to re-opening a seat that was temporarily closed. HR_ADMIN triggers this from the position record.

Microsoft Entra ID — Only Login Method
AVANIIS HR uses Auth.js v5 with Microsoft Entra ID OIDC as the sole authentication provider. There is no username/password login in production. The AZURE_AD_TENANT_ID, AZURE_AD_CLIENT_ID, and AZURE_AD_CLIENT_SECRET environment variables must be configured in Vercel. Dev-only credentials (hr.admin@avaniis.dev / demo) are only available when NODE_ENV=development.
Custom Fields Administration
Navigate to /settings/custom-fields to define entity-specific fields. Fields can be added to the persons or worker_assignments table. Supported types: TEXT, NUMBER, DATE, BOOLEAN, SELECT, MULTI_SELECT, URL. All labels must be provided in both English and Arabic. Custom fields appear in employee profiles, bulk import templates, and HR reports automatically once created.
Workflow SLA Rules
Navigate to /configuration/workflows to set SLA timers per approval step. SLA rules define the maximum hours before an approval step escalates. The Vercel cron job runs daily at 09:00 UTC and checks all PENDING_APPROVAL workflow instances against their SLA deadlines. Overdue approvals trigger escalation emails to the approver's manager. Delegation rules can be set to automatically reassign approvals during the approver's leave period.
Reaching This Module by Role
SUPER_ADMIN: Top-left navigation → Settings → Users
HR_ADMIN: Top-left navigation → Settings (Users option not visible)
All other roles: /users route returns 403 — redirected by middleware

Master Data is accessible to HR_ADMIN via: Navigation → Master Data (direct sidebar item). SUPER_ADMIN can also reach it via Settings → Master Data.

Troubleshooting Guide

Four common master data configuration issues, their root causes, and step-by-step resolution procedures.

Transfer Failing — Frozen Position or Grade Mismatch

Symptom
Transfer request submitted by HR Admin but workflow immediately errors with "Assignment blocked — position unavailable" or "Grade mismatch — salary outside band". Employee cannot be moved to the target position.
Root Cause A — Frozen Position
The target position has is_frozen=true. The system blocks all new worker_assignments to frozen positions regardless of approval status. This is enforced at the DB constraint level, not just the UI.
Root Cause B — Grade Mismatch
The target position is linked to a different grade than the employee's current grade, and the employee's salary falls outside the target grade's salary band (grade_salary_ranges table).
Resolution A (Frozen): Navigate to /master-data/positions → find target position → check is_frozen flag. If frozen, submit an unfreeze request with HR Director approval before retrying the transfer.
Resolution B (Grade Mismatch): Navigate to /master-data/grades → verify min/mid/max for target grade. Either adjust the employee's salary to fall within the target band, or select a different target position with a compatible grade. Finance sign-off required if salary change is needed.

Promotion Salary Blocked — grade_salary_ranges Not Defined

Symptom
HR Admin attempts to process a promotion that includes a salary increase but receives "Salary band validation failed — no band defined for grade G8" or the promotion form shows the salary field as read-only and locked at AED 0.
Root Cause
The target grade exists in the grades table but has no corresponding record in the grade_salary_ranges table, or the effective_from date for the salary range is in the future (past today's date) and no current record is active.
Verification Steps
Navigate to /master-data/grades → select the target grade → check the "Salary Band" section. If min/mid/max all show AED 0 or the band editor is empty, the grade_salary_ranges record is missing or not yet effective.
Resolution: Navigate to /master-data/grades → edit the target grade → enter min, mid, and max salary values → set effective_from to today or a past date → Save. Grade Band Validator will run. Once a valid band record exists with effective_from ≤ today, the promotion flow will accept the salary input. Finance notification will fire automatically for any existing employees whose salary falls outside the new band.

Employee in Wrong Entity — legal_entity_id Mismatch

Symptom
An employee appears under the wrong legal entity in the org chart, their payslips are being generated under the wrong WPS entity, or HR Admin cannot see the employee when filtering by the correct entity. Leave balances may also be calculated under wrong policies.
Root Cause
The employee's worker_assignment.legal_entity_id does not match the legal_entity_id of the position they are occupying. This can happen when positions are bulk-imported without specifying the entity, or after a department reparenting where the assignment was not updated in the same transaction.
Verification Steps
Navigate to /persons → find the employee → check their current assignment details. Compare the assignment's legal_entity_id with the position's legal_entity_id. They must match.
Resolution: Navigate to the person's profile → Assignments tab → edit current assignment → update legal_entity_id to match the position's entity. This change requires HR_ADMIN access and generates an audit log entry. Payroll should be re-run for the current month if the employee's WPS file has already been submitted — contact Finance to coordinate.

New User Cannot Log In — Entra ID SSO / Role Not Assigned

Symptom
A new employee or HR Admin reports they can see the Microsoft SSO login button but after authenticating with their corporate Microsoft account, they are redirected back to the login page with no error, or they land on a blank dashboard with no modules visible.
Root Cause A — No Role Assigned
The user has been authenticated by Microsoft Entra ID but no role has been assigned in the AVANIIS HR users table. Without a role, Auth.js middleware redirects the session to the login page (or shows an empty dashboard depending on the middleware version).
Root Cause B — Entra ID Tenant Mismatch
The user's Microsoft account belongs to a different Entra ID tenant than AZURE_AD_TENANT_ID. This causes the OIDC token to fail validation — Auth.js rejects the session silently.
Resolution A (No Role): Navigate to /users (SUPER_ADMIN only) → search for the user's email → assign the appropriate role (HR_ADMIN, MANAGER, EMPLOYEE, etc.) → click Save. The user should be able to log in immediately without needing to clear their browser cache.
Resolution B (Tenant Mismatch): Navigate to /settings/sso → verify AZURE_AD_TENANT_ID matches the user's Azure tenant. If the user is from a different tenant (e.g. a contractor from an external company), SUPER_ADMIN must configure Entra ID B2B guest access, or the user must use a Avaniis-issued Microsoft account.

## 1. Executive Summary

The AVANIIS HR database has **109 tables**. For a repeatable UAT cycle we partition them into three buckets:

| Bucket | Count | Action in cleanup | Rationale |
|---|---:|---|---|
| **PLATFORM CONFIGURATION** | 37 | **PRESERVE (never touched)** | Application behaviour built over months — workflows, approvals, letters, ARIA, compliance, leave/payroll rules, permissions, schedules, holidays. |
| **BUSINESS MASTER DATA** | 31 | **DELETE + RELOAD** | Org structure & people loaded for UAT validation. |
| **BUSINESS TRANSACTION DATA** | 41 | **DELETE + RELOAD** | Runtime records generated by exercising the system. |

**The framework is built around four anchors that must survive every cycle:**

1. **AVN-001** — the primary legal entity (`legal_entities.id = 11111111-1111-1111-1111-111111111111`, `entity_code = 'AVN-001'`).
2. **The Super Admin account** — `user_accounts` row where `avaniis_role = 'SUPER_ADMIN'`.
3. **The Super Admin's person record** — because `user_accounts.person_id` is **NOT NULL**, the Super Admin's `persons` row cannot be deleted without breaking the account.
4. **All 37 platform-configuration tables** — untouched.

**The single biggest design decision** (Section 6) is a genuine constraint conflict in your requirements: you asked to preserve **Approval Group Members**, but `approval_group_members.person_id` is a **NOT NULL foreign key to `persons`** — the very table being wiped. You cannot both "keep all approval group members" and "delete all persons." Section 6 lays out the two resolutions and recommends one. **This is the item requiring your sign-off before any script is written.**

## 2. Method (how this classification was produced)

- Extracted all 109 `pgTable` names (JS const → SQL name) directly from `drizzle/schema/*.ts`.
- Fanned out one analyst per schema file to read every table's `.references()` calls, `tenant_id` presence, self-references, `onDelete` behaviour, and effective-date/soft-delete columns.
- Cross-checked the result against your explicit NEVER-DELETE / DELETE lists and reconciled every disagreement (Section 5).
- Verified FK nullability on the four highest-risk config→person links by reading the source directly.

**Key structural finding:** Only **4 foreign keys in the entire schema use `ON DELETE CASCADE`**. Every other FK is `NO ACTION` / `RESTRICT` (Postgres default). **Consequence: deletion order is not optional — children must be deleted strictly before parents, or Postgres raises FK violations.** The cleanup script is therefore an *ordered* sequence, not a free-for-all `TRUNCATE`.

The 4 cascade FKs (informational — they self-clean):
- `approval_group_members.group_id → approval_groups` *(both preserved — irrelevant to cleanup)*
- `workflow_steps_v2.definition_id → workflow_definitions_v2` *(both preserved)*
- `workflow_step_instances.* → workflow_instances_v2` *(both transaction — child auto-purges with parent)*
- `medical_insurance_policy_settings.entity_id → legal_entities` *(config; cascades only if an entity is deleted — see Section 6.3)*

## 6. Decisions Required Before Scripting

### 6.1 🔴 PRIMARY DECISION — Approval Group Members vs Person Wipe

**The conflict:** `approval_group_members.person_id` is `NOT NULL REFERENCES persons(id)`. You asked to (a) never delete approval group members **and** (b) delete all persons. These are mutually exclusive — a membership row cannot point at a person that no longer exists.

| Option | What happens | Pro | Con | Repeatable? |
|---|---|---|---|---|
| **A — Re-point membership each cycle (RECOMMENDED)** | Delete `approval_group_members` rows during cleanup; `approval_groups` (the group definitions) are preserved. After reload, repopulate membership from the new person data (via seed or UI). | Truly clean wipe; reloaded org gets fresh, valid membership; no dangling FKs. | Membership must be re-established each cycle (one seed step). | ✅ Yes |
| **B — Preserve referenced persons** | Compute the set of persons referenced by `approval_group_members` and exclude them from the person wipe (alongside the Super Admin). | Membership literally survives. | Those persons can never be corrected/reloaded — defeats the purpose of UAT iteration; grows a "frozen" person island. | ⚠ Partial |

**Recommendation: Option A.** Treat **approval group *structure* as permanent config**, and **membership as per-cycle data** that is re-seeded after each org reload. This keeps the wipe complete and idempotent. *Your call.*

> ✅ **DECIDED (2026-06-03):** **Option A.** `approval_group_members` is **deleted every cycle** (Phase 4); `approval_groups` definitions are preserved. Membership will be re-added later (post-reload, via seed/UI). No person is preserved on account of group membership.

### 6.2 Config tables with NULLABLE person FKs (auto-handled)

`workflow_steps_v2.hierarchy_person_id` / `escalation_person_id` and `workflow_definitions_v2.fallback_person_id` are **nullable** FKs to `persons`. The cleanup will **NULL these columns** (a targeted `UPDATE`, not a delete) immediately before the person wipe, so the preserved workflow definitions stay intact while their person pointers are released. After reload, re-point them via config UI/seed. **Confirm you accept a one-time NULLing of these three columns.**

> ✅ **DECIDED (2026-06-03): ACCEPTED** (default applied). Phase 0 NULLs `workflow_steps_v2.hierarchy_person_id`, `workflow_steps_v2.escalation_person_id`, and `workflow_definitions_v2.fallback_person_id`. Re-point after reload.

### 6.3 Non-AVN-001 configuration rows

If any of the 30 entity-scoped config tables hold rows for a *non-AVN-001* entity created during UAT, deleting that entity would (for `medical_insurance_policy_settings`) cascade-delete the row, and for all others raise an FK violation. **Decision:** the framework will **only delete config rows whose `legal_entity_id` is a non-AVN-001 entity being removed**, and never touch AVN-001-scoped config. Recommended default: **all platform config is AVN-001-scoped; non-AVN-001 entities have no config rows.** Confirm, or we add an explicit pre-check.

> ✅ **DECIDED (2026-06-03): default applied** — assume all config is AVN-001-scoped. `VERIFY_UAT_CLEANUP.sql` will include a guard that **fails loudly** if any config row references a non-AVN-001 entity, so a wrong assumption surfaces before the wipe rather than after.

### 6.4 Audit log retention

`audit_log` is INSERT-only and immutable by design. Options: **(A)** purge it with the rest of the transaction data each cycle (clean slate — recommended for UAT), or **(B)** preserve it across cycles (full history, but it will reference deleted persons via `actor`/`resource` UUIDs — those are plain UUID columns, **not FKs**, so no integrity break). **Recommendation: purge in UAT, preserve in production-readiness cycle.** Same applies to `workflow_audit_log` (which *does* have FKs to workflow runtime, so it auto-purges with its parents).

> ✅ **DECIDED (2026-06-03): PURGE each UAT cycle.** `audit_log` is wiped in Phase 1. (Switch to preserve for the final production-readiness dress rehearsal.)

### 6.5 Payroll config/master split

Confirm: `grade_salary_ranges` = preserve (config); `payroll_definitions`, `salary_elements`, `payroll_assignments` = delete (org/person-scoped). If `payroll_definitions` rows are considered permanent AVN-001 config rather than reloadable master data, move it to Bucket A.

> ✅ **DECIDED (2026-06-03): DELETE all three** as reloadable master data. `grade_salary_ranges` stays preserved as config. `payroll_definitions` deleted in Phase 7.

## 7. Dependency Map & Deletion Order

Because almost all FKs are `RESTRICT`, deletion runs **leaf → root**. The order below is FK-safe (every table is deleted only after all tables that reference it). Grouped into ordered phases; within a phase, order is interchangeable.

### Phase 0 — Neutralize preserved-config person pointers (UPDATE, not DELETE)
```
UPDATE workflow_steps_v2        SET hierarchy_person_id = NULL, escalation_person_id = NULL;
UPDATE workflow_definitions_v2  SET fallback_person_id  = NULL;
-- (approval_group_members handled per Section 6.1 decision)
```

### Phase 1 — Transaction leaves (deepest children first)
```
workflow_notification_queue → workflow_email_tokens → workflow_audit_log
→ workflow_step_instances → workflow_instances_v2          (cascade handles steps→instance)
workflow_instances                                          (v1)
letter_email_jobs → employee_letters → document_files
payroll_results, eosb_calculations, wps_sif_records,
  gpssa_contributions, dews_contributions, vss_contributions,
  gl_journal_lines, timesheet_entries
timesheet_periods
attendance_exceptions → attendance_records, device_punch_raw, device_sync_log
absence_balances, absence_entries, accommodation_requests
medical_insurance_enrolments
onboarding_checklist_items → onboarding_checklists
probation_reviews, hiring_requests, transfer_requests
notification_log, approval_delegations, blackout_periods,
  org_hierarchy_snapshots, events
refresh_tokens            (except Super Admin's user_account_id)
```
> `eosb_calculations → employment_actions` and the payroll children → `payroll_runs`: so delete eosb/results/contributions/timesheets **before** `payroll_runs`.

### Phase 2 — Payroll runs & employment actions
```
payroll_runs
employment_actions        (references worker_assignments — delete before Phase 3)
```

### Phase 3 — Identity (except Super Admin)
```
user_accounts             WHERE avaniis_role <> 'SUPER_ADMIN'
                          (and primary_email <> 'super.admin@avaniis.dev')
```

### Phase 4 — Master: assignments & person-linked structures
```
salary_elements           (refs worker_assignments)
payroll_assignments, work_schedule_assignments
worker_assignments
leave_plan_enrolments
contracts                 (self-ref previous_contract_id → delete in one statement)
grade_history, department_history, location_history,
  job_history, position_history
approval_group_members    (per Section 6.1 — Option A)
workflow_delegation_rules
```

### Phase 5 — Person sub-records (documents last among them)
```
person_education, person_professional_certs, person_dependents
  → (these reference person_documents)
person_contacts, person_addresses, person_bank_details, person_emergency_contacts
person_documents          (self-ref + referenced by above; delete after them)
```

### Phase 6 — Persons (except preserved set)
```
persons  WHERE id NOT IN (preserved set)
-- preserved set = Super Admin's person_id
--               + [Option B only] persons referenced by preserved config
-- self-refs (line_manager_id etc.): single DELETE statement resolves them,
--   or NULL the self-ref columns first for safety.
```

### Phase 7 — Org structure (children → parents; mind self-refs)
```
positions      (self-ref reports_to_position_id)
jobs           (self-ref)
departments    (self-ref parent_department_id)
business_units
locations       (self-ref)
projects        (self-ref)
grades          (self-ref)
payroll_definitions
```
> For each self-referencing table, run `UPDATE t SET <self_fk> = NULL` first, then `DELETE`, to avoid intra-table ordering issues.

### Phase 8 — Legal entities (except AVN-001)
```
legal_entities WHERE id <> '11111111-1111-1111-1111-111111111111'
               AND entity_code <> 'AVN-001'
```

**Reverse order = reload order.** Reload runs Phase 8 → Phase 1 (entities → org → persons → assignments → transactions).

## 8. Repeatability, Idempotency & Safety

| Property | How it is guaranteed |
|---|---|
| **Idempotent** | Every step is a `DELETE … WHERE` / `UPDATE … WHERE`. Re-running on an already-clean DB deletes 0 rows — no error, no side effect. No `TRUNCATE` (which would fight FKs and reset identities). |
| **No orphans** | Strict leaf→root order + Phase 0 NULLing means no child ever outlives its parent and no preserved row ever dangles. |
| **No FK violations** | Order derived from the actual FK graph; verified against all 109 tables. |
| **Tenant-scoped** | Every `DELETE` carries `WHERE tenant_id = '00000000-0000-0000-0000-000000000001'` (defence-in-depth; single-tenant today). |
| **Preserve guards** | Super Admin (`avaniis_role='SUPER_ADMIN'`), AVN-001 entity, and all 37 config tables are explicitly excluded. |
| **Atomic** | Entire cleanup wrapped in one `BEGIN … COMMIT`. Any error → `ROLLBACK`, DB untouched. |
| **Repeatable N times** | Load → validate → run cleanup → reload → repeat. Config is never touched, so platform behaviour is identical every cycle. |

## 9. Rollback Strategy (defence in depth — three layers)

1. **Neon branch (PRIMARY — recommended).** Before every cleanup, create a Neon branch (`uat-pre-cleanup-<date>`). Instant, copy-on-write, free. If anything is wrong, repoint the app to the branch or restore it — full point-in-time recovery in seconds. *This is the real safety net; SQL rollback only covers in-transaction failures.*
2. **Transaction wrapper.** `BEGIN; … ; COMMIT;` — any FK error or exception mid-run rolls the whole thing back automatically.
3. **Logical dump (optional).** `pg_dump` of the 72 delete-scope tables to a timestamped file before running, for off-platform restore. (Note: `psql`/`pg_dump` are not installed on the dev Mac — use Neon's branch/export, per project convention.)
